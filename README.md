# Summon Local GPT-OSS

English | [繁體中文](README.zh-TW.md)

Run gpt-oss (120b or 20b) locally with vLLM:

- **vLLM + LiteLLM** (the main setup): a LiteLLM proxy in front of vLLM serves an OpenAI-compatible API that requires a key
- **vLLM only**: use vLLM's own OpenAI-compatible API directly, without LiteLLM and without a key
- **Plus Open WebUI**: a chat UI in the browser that reaches vLLM through LiteLLM

Every service binds to `127.0.0.1` only, so only this machine can reach it. Plain Python environments instead of Docker: each service gets its own uv-managed venv inside the repo.

```
browser ──> Open WebUI :OPENWEBUI_PORT ──┐  (bash install.sh full)
client  ─────────────────────────────────┴──> LiteLLM :LITELLM_PORT ──> vLLM :VLLM_PORT (gpt-oss)
```

## Quick start

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # install uv (once)
cp .env.example .env                               # fill in HF_HOME, LITELLM_MASTER_KEY, ...
```

| You want | Install | Start |
|---|---|---|
| API (vLLM + LiteLLM, with key) | `bash install.sh` | `bash start.sh` |
| vLLM only (no key) | `bash install.sh` | `bash vllm_start.sh` |
| Chat UI (the API plus Open WebUI) | `bash install.sh full` | `bash start.sh` |

- The weights must already be in `HF_HOME`, see [Requirements](#requirements); every `.env` entry is explained in [Configuration](#configuration)
- Usable once the ready banner is printed (about 8 minutes for 120b on DGX Spark), see [Starting](#starting); Ctrl-C stops it, see [Stopping](#stopping)
- For API examples see [Calling the API](#calling-the-api)

## Platforms

| Platform | Locked vLLM | NVIDIA driver | Status |
|---|---|---|---|
| DGX Spark (GB10, aarch64) | `vllm==0.33.0` (CUDA 13.0) | ≥ 580 | ✅ Verified: `backend`, `full`, 120b, 20b |
| DGX server (H200 / H100 / A100, x86_64) | `vllm==0.19.1` (CUDA 12.8) | ≥ 570 | ⚠️ Unverified (`backend` ran on H200 before; these changes were not tested on x86_64) |
| Generic x86_64 NVIDIA machine | Same as above | ≥ 570 | ⚠️ Unverified |
| Mac (Apple Silicon) | None | — | ❌ Not supported yet: there is no `requirements/vllm.arm64.txt`, so `install.sh` stops with an error |

- `install.sh` picks `requirements/vllm.<arch>.txt` by `uname -m`; LiteLLM and Open WebUI share one cross-platform lock each
- The aarch64 lock also installs `flashinfer-cubin` (about 1.7 GB to download, about 7 GB installed, from FlashInfer's own index): precompiled FlashInfer kernels. Without it vLLM checks NVIDIA's artifactory on every start and FlashInfer downloads kernels on demand
- With driver ≥ 580 on x86_64, `requirements/vllm.x86_64.in` can move to a CUDA 13 release (vLLM 0.20 and later)
- Check `Driver Version` with `nvidia-smi` before installing

## Files

| File | Purpose |
|---|---|
| `install.sh` | Creates the venvs with uv and installs the locked versions: `backend` (default) or `full` |
| `start.sh` | Starts every installed service with one command; Ctrl-C stops them all |
| `vllm_start.sh` | Starts vLLM alone and prints a greeting once it is ready |
| `litellm_start.sh` | Starts LiteLLM alone |
| `openwebui_start.sh` | Starts Open WebUI alone (waits until vLLM is ready); all Open WebUI settings live here |
| `env.sh` | Shared by the `*_start.sh` scripts: reads `.env` and derives the model name and the `GPU_MEMORY_UTILIZATION` default from `MODEL` |
| `config.yaml` | LiteLLM config with a single model (named after `MODEL`) |
| `.env.example` | Settings template; copy it to `.env` and fill it in |
| `requirements/*.in` | Direct dependency versions; vLLM is split by CPU architecture (`vllm.x86_64.in`, `vllm.aarch64.in`) |
| `requirements/*.txt` | Fully locked dependencies, generated by `lock.sh` |
| `lock.sh` | Re-locks after you change a `*.in` file |

## Requirements

| Item | Requirement |
|---|---|
| GPU | NVIDIA GPU. 120b needs room for 60.8 GiB of weights plus the KV cache: DGX Spark, a single 80 GB GPU (`GPU_MEMORY_UTILIZATION=0.9`), or two or more GPUs; the 20b weights are about 13 GiB |
| NVIDIA driver | See [Platforms](#platforms); `install.sh` checks it and warns |
| Disk | `HF_HOME`: about 61 GiB for 120b, about 13 GiB for 20b. venvs (measured on DGX Spark): `backend` about 17 GB (about 7 GB of it is `flashinfer-cubin`), `full` adds about 1.5 GB (Open WebUI shares torch and the CUDA packages with vLLM) |
| System | Linux x86_64 or aarch64, Bash ≥ 5.1 (`start.sh` uses `wait -n <pid>`) |
| Python | [uv](https://docs.astral.sh/uv/); the venvs use uv-managed Python 3.12 (downloaded automatically the first time) |
| Other | `curl`; `openssl` to generate the key |

Install uv with the official installer (the system Python on Ubuntu 24.04 does not allow a plain `pip install`):

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

`HF_HOME` must contain:
  - `hub/models--openai--gpt-oss-120b` or `hub/models--openai--gpt-oss-20b` (the weights, depending on `MODEL`)
  - `tiktoken_encodings/` (`*.tiktoken` files, which harmony needs offline)

If the weights are missing, download them after installing with the `hf` in the venv (needs network; `original/` and `metal/` hold weights in other formats that vLLM does not use):

```bash
HF_HOME=/path/to/huggingface .venv-vllm/bin/hf download openai/gpt-oss-20b --exclude 'original/*' --exclude 'metal/*'
```

## Installation

```bash
bash install.sh        # backend: vLLM + LiteLLM (same as bash install.sh backend)
bash install.sh full   # backend plus Open WebUI
```

- Safe to re-run; existing venvs are synced to the locked versions
- `start.sh` starts Open WebUI only if `.venv-openwebui` exists; to go back to backend only after a `full` install, delete `.venv-openwebui`

To upgrade a version, edit `requirements/*.in`, then run:

```bash
bash lock.sh
bash install.sh   # or bash install.sh full
```

## Configuration

```bash
cp .env.example .env
```

| Variable | Description |
|---|---|
| `HF_HOME` | Root of the HF cache (weights and tiktoken) |
| `MODEL` | `120b` or `20b` (`120b` when unset); selects the model vLLM loads and the model name `gpt-oss-120b` / `gpt-oss-20b` |
| `VLLM_PORT` | vLLM port (default 28000) |
| `LITELLM_PORT` | LiteLLM port, which API clients connect to (default 24000) |
| `OPENWEBUI_PORT` | Open WebUI port, which the browser connects to (default 28080) |
| `GPUS` | GPU indices, e.g. `0` or `2,3`; tensor parallel size = number of GPUs |
| `GPU_MEMORY_UTILIZATION` | Optional; fraction of each GPU's memory vLLM may use. When unset, `env.sh` picks a default by `MODEL`, measured on DGX Spark: 0.75 for 120b, 0.35 for 20b. Both leave about 25 GiB of KV cache (about 700k tokens for 120b, about 1M for 20b), enough for 5 or more concurrent requests at 131k context |
| `LITELLM_MASTER_KEY` | Key for calling LiteLLM; Open WebUI also uses it to connect to LiteLLM |
| `OPENWEBUI_FILE_UPLOAD` | File upload in Open WebUI chats: `false` (default) or `true`, see [File upload](#file-upload) |

Generate `LITELLM_MASTER_KEY` with:

```bash
echo "sk-$(openssl rand -hex 32)"
```

## Starting

```bash
bash start.sh
```

- No venv needs to be activated first; the scripts call the executables in the repo's venvs directly
- LiteLLM is ready within seconds. vLLM has to load the weights and is usable once it prints `===== gpt-oss-120b is ready =====` (`gpt-oss-20b` for 20b). Measured on DGX Spark: about 8 minutes for 120b (mostly reading the weights), about 3.5 minutes for 20b
- With Open WebUI installed, it starts after vLLM is ready; open the browser once `===== Open WebUI is ready: http://127.0.0.1:28080 =====` is printed
- If any service dies, the others are stopped too
- If a port is already in use, the script stops with an error instead of starting

Start a single service:

```bash
bash vllm_start.sh
bash litellm_start.sh
bash openwebui_start.sh   # waits for vLLM to be ready first
```

## Open WebUI

- Single local user: no sign-up or sign-in, it opens straight to the chat; the only user is an admin
- Connects to LiteLLM only: not directly to vLLM, not to Ollama
- Chat only: web search, knowledge bases, image generation, code interpreter / code execution, tools / functions, memory, notes, channels and the like are all turned off. The background follow-up suggestions, tags and autocomplete are off as well; only automatic chat titles remain
- Because the only user is an admin, and Open WebUI does not apply permissions to admins, some entries cannot be removed: Workspace, Playground and Admin Panel in the bottom-left menu, and "+" → "Add Context" in the input box. The features listed above are turned off globally; of these entries only "Attach Webpage" still works (when you paste a URL, the server fetches that page)
- No outbound connections at runtime (`OFFLINE_MODE=True`): no model downloads, no update checks
- gpt-oss's reasoning shows up as an expandable block, and the answer shows normally

### Settings come from the script

By default Open WebUI writes its settings into its own database on the first start, and environment variables stop taking effect after that. `openwebui_start.sh` sets `ENABLE_PERSISTENT_CONFIG=False`, so the script's settings win on every start:

- Changes made in the admin settings are reverted on restart; to change something for good, edit `openwebui_start.sh`
- Chat history is stored in `.openwebui-data/` (already in `.gitignore`)
- To reset everything (chat history included): stop the services, then delete `.openwebui-data/`

### File upload

Off by default. When it is on, Open WebUI uses an embedding model (`sentence-transformers/all-MiniLM-L6-v2`) to process uploaded files. The runtime is offline, so download the model into `HF_HOME` first (about 0.9 GiB; loading offline checks that the snapshot is complete, so a partial download does not work):

```bash
HF_HOME=/path/to/huggingface .venv-openwebui/bin/hf download sentence-transformers/all-MiniLM-L6-v2
```

Then set `OPENWEBUI_FILE_UPLOAD=true` in `.env` and restart. Without the model Open WebUI still starts, but uploaded files cannot be processed, and the log shows `IncompleteSnapshotError` or `Error loading SentenceTransformer`.

## Calling the API

OpenAI-compatible API; the model name is `gpt-oss-120b` or `gpt-oss-20b` (depending on `MODEL`):

```bash
set -a; source .env; set +a
curl -s "http://127.0.0.1:$LITELLM_PORT/v1/chat/completions" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model": "gpt-oss-120b", "messages": [{"role": "user", "content": "Hello"}]}'
```

## Stopping

- In the foreground: Ctrl-C (once is enough; pressing it again while stopping is ignored)
- From another terminal: `kill <PID of start.sh or a *_start.sh>` (sends TERM; the script stops its own service, then exits)
- vLLM stops within seconds once it is ready; while it is still loading weights it ignores TERM, and `vllm_start.sh` force-stops it after 15 seconds (measured on DGX Spark: about 3 seconds when ready, about 15 seconds while loading)
- Do not stop the scripts with `kill -9`: vLLM runs in its own process group, so it stays behind and keeps holding memory when its script is killed. If that happens (`nvidia-smi` shows `VLLM::EngineCore`), clean it up with `pkill -KILL -f 'vllm serve|VLLM::EngineCore'` (this ends every vLLM of your user)

## Notes

- On a shared server, `127.0.0.1` is shared by all users: a service fails to start if its port is taken, and other users on the machine can reach your ports (the vLLM side has no authentication; Open WebUI has sign-in turned off)
- Use 1, 2, 4 or 8 GPUs in `GPUS` (the tensor parallel size must divide the number of attention heads)
- `GPU_MEMORY_UTILIZATION`: a single H100 80 GB needs 0.9 to fit the 60.8 GiB of 120b weights. On DGX Spark the GPU shares memory with the system, so a high fraction squeezes the memory left for the system and Open WebUI
- The first time vLLM starts on DGX Spark, FlashInfer compiles a few kernels for GB10 on the spot (with the `ninja` in the venv) and caches them in `~/.cache/flashinfer`; later starts skip the compile
- No outbound connections at runtime: vLLM only reads `HF_HOME` and does not report usage stats (`VLLM_NO_USAGE_STATS=1`), LiteLLM uses its bundled model cost map (`LITELLM_LOCAL_MODEL_COST_MAP=True`), and Open WebUI is covered above. All downloads happen at install time (`install.sh`, the weights and the embedding model)
